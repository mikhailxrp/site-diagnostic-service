# Current Task

## Фаза
Phase 5 — Для клиента и углублённые проверки (таск 5 — ИИ-текст для клиента) — ✅ Завершён

## Задача
Добавить шаг `ai_client`, который после технического ИИ-вывода безопасно формирует простое клиентское резюме и тексты для находок этой диагностики, сохраняет ответ в `ai_results`, заполняет `findings.client_text` и при любом отсутствии пригодного ИИ-результата оставляет клиентский отчёт работоспособным на шаблонах.

## Образец
Нового экрана и утверждённого HTML-прототипа нет: каталога `.docs/ref/prototypes/` в проекте нет. Клиентская версия уже реализована в таске 4 на стандартных компонентах локального Tabler. Отдельный макет не создаётся: клиентское резюме добавляется в существующий поток страницы компонентом `card` или `alert`, без новых CSS и JavaScript.

Состояния существующего экрана:
- успешный `ai_client` — перед группами находок показано безопасное клиентское резюме, а внутри групп используются сохранённые `client_text`;
- шаг пропущен, упал или ещё не существовал у старой диагностики — резюме отсутствует, группы полностью строятся по шаблонам таска 4;
- повторный ИИ-анализ — старые клиентские тексты не остаются на экране, показывается только результат нового запуска либо шаблонный fallback.

## Как это работает
1. `ai_client` идёт сразу после `ai_summary`, входит в полный запуск диагностики и в `getAiSteps()`, поэтому автоматически участвует в существующем перезапуске только ИИ-анализа. Шаг не обращается к проверяемому сайту: диагностику, находки и последний успешный итог `summary` он читает из БД.
2. Используется настройка `model_summary` через существующий `resolveModelSetting()` (пустая настройка получает проектную модель по умолчанию). Если `ROUTERAI_API_KEY` отсутствует или невалиден, шаг получает `skipped`; клиентский отчёт продолжает работать по шаблонам. Ошибка API, промпта или схемы ответа даёт обычный для ИИ-шагов `failed`, а не останавливает остальные шаги воркера.
3. `ClientTextAnalysis` следует существующему контуру `AiTask`: системный промпт из `config/prompts/client.txt`, входные данные отдельным JSON-сообщением, строгая JSON-схема и запись в `ai_results` с `task = client_text`. В запрос не попадают API-ключ и несвязанные данные других диагностик.
4. Ответ содержит одно общее клиентское резюме и список элементов `finding_id + text`. Допустимы только положительные id из переданного набора находок этой диагностики; чужие, несуществующие и повторные id, пустые тексты и элементы неверной формы отбрасываются и учитываются в сообщении шага.
5. Перед сохранением каждый текст проходит защитный фильтр клиентского отчёта. Текст с URL, IP, путём к файлу, версией ПО, HTTP-кодом или сырым сообщением об ошибке не записывается и не выводится; для такой находки остаётся безопасный шаблон. Те же правила применяются к общему резюме. Фильтр работает в коде и не полагается только на промпт.
6. После успешного разбора ответа обновление выполняется атомарно для одной диагностики: сначала всем её находкам ставится `client_text = NULL`, затем валидные тексты записываются только по разрешённым id с условием `diagnostic_id`. Поэтому пропущенные моделью находки возвращаются к шаблонам, а частично применённого набора нет.
7. При подготовке перезапуска ИИ старые `client_text` также очищаются в той же транзакции, где сбрасываются ИИ-шаги и удаляются старые ИИ-находки. Если новый запуск пропущен или завершился ошибкой, старый текст не маскируется под свежий результат.
8. Клиентский отчёт рассматривает последнюю по `id` запись `ai_results` с задачей `client_text` и использует её резюме только когда текущий шаг `ai_client` имеет статус `done`, а сама последняя запись — `ok`. Поэтому более старый успешный ответ не всплывает после нового `skipped` или `failed`. В данные View переносится только прошедшее фильтр резюме; сырые `response_text`, request JSON, модель, токены, id и технические поля не передаются.
