# Phase 5 — Для клиента и углублённые проверки

## Цель
Сервис проверяет открытые служебные файлы и сценарий «товар → корзина → оформление» (заказ не отправляется);
владелец выгружает полный или клиентский отчёт в PDF, повторяет диагностику и видит, что исправлено, что осталось
и что появилось.

## Статус
🔄 В работе

> План перепроверен 16.11.2026 с учётом сделанного в Фазах 0–4 (`phase-init.md`).
> Дизайн: образцов нет — экраны из стандартных компонентов Tabler (решение владельца, 15.11.2026).
> Экраны: отчёт — `src/Views/pages/diagnostic.php` (данные готовит `src/Services/ReportBuilder.php`),
> компоненты — `src/Views/components/`.

**Контекст (проверено 16.11.2026 по коду):**
- Шаги воркера (`DiagnosticRunner`): `availability`, `stack`, `outdated`, `vulnerabilities`, `crawl`, `resources`,
  `seo`, `browser`, `pagespeed`, `ai_problem`, `ai_visual`, `ai_summary`. Шагов `exposed_files` и `checkout` нет.
- В БД уже есть всё нужное: `findings.fingerprint` (заполняется), `findings.client_text` (пустая),
  `ai_results.task = 'client_text'`, `diagnostics.previous_id` (ставится при создании по `host`). Миграций не нужно.
- Типовые адреса корзины и оформления по CMS — в `data/shop-patterns.php`; поле «Адрес товара» (`product_url`)
  в форме уже есть.

**Решения:**
- Новые шаги: `exposed_files` — после `seo`; `checkout` — после `browser`; `ai_client` — после `ai_summary`
  (входит в перезапуск ИИ-анализа).
- Сценарий корзины **не отправляет заказ**: кнопки «Оформить» / «Подтвердить» не нажимаются никогда, на странице
  оформления все POST-запросы блокируются перехватом сети (Fetch domain). Добавление в корзину разрешено — меняет
  только сессию.
- Своего тестового магазина нет: «заказ не создан» проверяется по логу перехвата — на странице оформления не ушло
  ни одного POST (решение владельца, 16.11.2026).
- ИИ-текст для клиента — модель из `model_summary`, отдельной настройки нет (решение владельца, 16.11.2026).
- Клиентский отчёт работает без ИИ: тексты по шаблонам категорий; `client_text` от ИИ, если есть, важнее шаблона.
- PDF — печать HTML-файла через тот же Chrome (`printToPDF`); сессия в браузер не передаётся.
- Сравнение — по `fingerprint`; ИИ-находки выводятся отдельно (их формулировки меняются от запуска к запуску).
- Размер читаемых файлов, тайм-ауты сценария и печати — именованные константы (лимитов обхода нет, решение
  владельца).

**Сайты для ручной проверки:** https://sudar.su/, https://cleansan.ru/, https://www.citilink.ru/ (как в Фазах 2–4).

## Таск 1 — Открытые служебные файлы

**Статус:** ✅ Завершён

**Образец:** без UI (находки выводятся существующим компонентом `finding.php`)

**Цель таска:**
Шаг `exposed_files` (после `seo`) проверяет фиксированный список путей: `.git/HEAD`, `.git/config`, `.env`,
бэкапы конфигов (`wp-config.php.bak` и т. п.), дампы `*.sql` и архивы, `phpinfo.php` / `info.php`, `adminer.php`,
логи (`error_log`, `wp-content/debug.log`). Сначала запрашивается случайный несуществующий адрес — эталон
«мягкого 404». Каждый файл читается с ограничением размера (`Range` + обрыв загрузки в curl); настоящий файл
отличается от заглушки по признаку содержимого (`ref:` в `.git/HEAD`, `KEY=` в `.env`, magic bytes архивов,
`phpinfo()` в HTML).

**Что нужно создать/изменить:**
- `data/exposed-files.php` — путь, признак содержимого, серьёзность
- `src/Services/Checks/ExposedFilesCheck.php`
- `src/Services/HttpClient.php` — запрос с пределом размера ответа (если такого режима ещё нет)
- `src/Services/DiagnosticRunner.php` — шаг `exposed_files`
- `tests/Unit/ExposedFilesCheckTest.php`

**Definition of Done:**
- [ ] Сайт, отдающий 200 с главной на любой адрес, не даёт ложных находок (тест)
- [ ] Открытый `.env` / `.git` → находка `critical`; в `evidence`, отчёт и лог попадает только факт доступности
      и имя признака, значения секретов — нет
- [ ] Читается не больше `EXPOSED_FILE_MAX_BYTES` каждого файла (константа)
- [ ] Проверено вживую на 2–3 сайтах
