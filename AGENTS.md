# AGENTS.md — правила работы агента

Этот файл — основная точка входа для агента и действует на весь репозиторий.
`CLAUDE.md` сохранён только как совместимая ссылка на этот документ.

## Проект

Site Diagnostics — локальный однопользовательский инструмент экспресс-диагностики интернет-магазинов.
Сервис собирает проверяемые факты через HTTP, разбор HTML и headless Chrome, а ИИ используется только для их интерпретации.
Результат — технический или клиентский отчёт, включая экспорт в PDF.

Среда: Windows, OpenServer, PHP 8.x, MySQL 8. Проект не публикуется в интернете.

## Обязательные правила

Соблюдай эти документы без ослабления и не заменяй их собственными соглашениями:

- `.claude/rules/general.md` — общие правила для любой задачи;
- `.claude/rules/php.md` — обязательные правила для всех PHP-файлов;
- `.claude/rules/design.md` — обязательные правила для Views, CSS, JS и UI-задач;
- `.docs/dod-global.md` — глобальные критерии готовности каждого таска.

Тематические правила не дублируются здесь. Перед изменением соответствующих файлов открой нужное правило и следуй ему как есть.

## Автономный рабочий цикл

### 1. Ориентация

1. Определи текущую фазу по `.docs/phases/_status.md`.
2. Прочитай `TASK.md`, соответствующий `phase-N.md` и `.docs/dod-global.md`.
3. Открой обязательные тематические правила и документы, относящиеся к задаче.
4. Изучи существующий код и тесты, найди готовые функции и принятые в проекте шаблоны.

Не копируй промпты вручную и не требуй этого от пользователя. Регламенты из `.docs/prompts/` агент применяет самостоятельно.

### 2. Планирование

Для нетривиальной задачи кратко определи порядок работ и затрагиваемые файлы. При многошаговой работе веди список задач через доступный инструмент отслеживания.

Не жди отдельного подтверждения локальных обратимых действий в рамках уже выданной задачи. Если пользователь просил создать или обновить план, запись соответствующего документа является частью запроса.

### 3. Реализация

- Выполняй задачу целиком, а не останавливайся после анализа или плана.
- Соблюдай Scope и Out of scope из `TASK.md`; не делай попутный рефакторинг.
- Scope — граница изменений, а не требование менять все перечисленные файлы.
- Если без изменения вне Scope задачу выполнить нельзя, объясни причину и согласуй именно это расширение.
- Принимай самостоятельно обратимые технические решения, которые не меняют продуктовые требования.
- Сохраняй существующие архитектурные соглашения и не добавляй зависимости без необходимости.

### 4. Проверка

- Проверь каждый применимый пункт DoD из `TASK.md` и `.docs/dod-global.md`.
- Запусти `composer test` и более точечные проверки, если они нужны для затронутого кода.
- Проверь исходный пользовательский сценарий end-to-end: реальными вызовами, через интерфейс или воркер, а не только загрузкой классов.
- Для UI следуй `.claude/rules/design.md`, включая обязательные ширины и состояния экрана.
- Проверь `storage/logs/app.log` на новые ошибки и warnings, если таск затрагивает выполняемый PHP-код.
- Не отмечай критерий выполненным без фактической проверки. Невозможное или непроверенное явно назови в итоге.

### 5. Завершение

Когда все применимые критерии выполнены:

1. Отметь DoD в `TASK.md`.
2. Обнови статус таска в текущем `phase-N.md`.
3. Если завершена вся фаза, обнови `.docs/phases/_status.md` и при необходимости создай отчёт фазы.
4. Добавь запись в `.docs/dev-log.md` сверху: дата, реализованное, результаты проверок, следующий шаг.
5. В итоговом ответе перечисли изменения, выполненные проверки и оставшиеся ограничения.

Дополнительное подтверждение для закрытия полностью проверенного таска не требуется. Если проверки не пройдены или реализация неполна, таск не закрывай.

## Когда всё же нужен вопрос

Спрашивай только если ответ нельзя получить из кода и документации и выбор влияет на результат:

- неоднозначное продуктовое требование с существенно разными решениями;
- отсутствующий обязательный дизайн-образец;
- необходимое расширение Scope;
- рискованное, труднообратимое или внешнее действие;
- необходимые секреты или доступы.

Не спрашивай разрешения на обычное чтение кода, локальное редактирование в рамках задачи, запуск тестов и исправление ошибок в пределах Scope.

## Работа с изменениями пользователя

Перед редактированием учитывай текущее состояние рабочей директории. Не перезаписывай и не откатывай чужие незакоммиченные изменения. Не создавай commit, push или другие Git-операции с историей без отдельного запроса.
